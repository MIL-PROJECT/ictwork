# OMNIS Desktop

최신 배치 정리 실행본: `output/OMNIS-Layout-Polish-Windows-x64/OMNIS.exe`. 업무 통계 보기 조건을 상단으로 이동하고 통합상황판의 보조 문구·경보 요약줄을 정돈했다. 자세한 변경·검증은 `docs/UI_LAYOUT_POLISH.md`, 실행 근거는 `output/layout-polish/`에 보관한다.

Windows x64 시연 실행본. 배포 폴더 전체를 유지한 상태에서 **OMNIS.exe**를 실행한다. 첫 실행은 DB 초기화와 마이그레이션 때문에 시간이 걸릴 수 있다. 앱 창에서 시연 계정 **bn1-co1-admin**과 암호 **Local-Demo-Init!26**으로 로그인한다.

Electron이 포함된 Java 17로 Spring Boot WAR를 실행하고 MySQL 8.0의 시연 DB를 관리한다. 두 서비스는 매 실행에 정한 포트를 사용하며 127.0.0.1에서만 연결된다. 일반 창 닫기에서 Java 프로세스를 종료한 뒤 MySQL에 정상 종료를 요청한다.

시연 데이터와 로그는 %APPDATA%\OMNIS Desktop Main\service 에 저장된다. 기존 웹 시연 DB와 분리된다. 폴더를 옮겨도 같은 Windows 사용자 계정에서 다시 열면 데이터가 유지된다. 합성 데이터 시연용 계정이 포함되어 있다.

## 재빌드

Java 17과 pnpm을 사용해 src/backend에서 gradlew.bat bootWar를 실행한다. 그 WAR와 정식 Windows x64 Electron 배포 폴더, Java 17 런타임, MySQL 8.0 ZIP 배포본 압축 해제 폴더를 Package-Windows.ps1의 인수로 전달한다. Destination은 새 디렉터리를 지정한다.

Windows 실행 파일에 OMNIS 아이콘을 넣으려면 ResourceEditor 인수에 Windows용 rcedit 실행 파일을 지정한다.

## 단일 설치 파일 (2026-11-07)

`Build-Setup.ps1`은 인수로 지정한 폴더형 실행본을 오프라인 NSIS 설치 파일 `Setup.exe` 하나로 묶는다. Electron·Java·MySQL·WAR와 Microsoft 서명된 Visual C++ x64 재배포 패키지를 포함한다. 기본 설치 위치는 현재 사용자의 `%LOCALAPPDATA%\Programs\OMNIS Final`이다. 필수 C++ 런타임이 없는 PC에서만 해당 런타임 설치를 위한 관리자 승인이 필요하다.

Windows MySQL은 현재 ANSI 코드 페이지에 호환되는 경로를 사용해야 한다. 공백이 있는 실행 파일의 `argv[0]`을 이름만 전달하고, 한글 설치·사용자 경로는 `windows-ansi.exe`로 Windows 기본 인코딩의 MySQL 옵션 파일에 기록한다. 이 작은 변환기는 `windows-ansi.c`에서 MSVC `/MT`로 빌드하며 `KERNEL32.dll`만 의존한다. 변환할 수 없는 문자를 조용히 바꾸지 않고 오류로 처리한다. `Build-PathHelper.ps1`은 패키징 전 변환기를 빌드하고, `Package-Windows.ps1`이 실행본에 포함한다.

변환기 재빌드에는 MSVC Build Tools와 Windows 10 SDK가 필요하다. 변환기 회귀 검사는 `python desktop/test-path-helper.py`로 한글 입출력 경로, 설정 내용의 정확성, 잘못된 UTF-8·표현할 수 없는 경로의 거부와 이전 설정 보존을 확인한다.

빌드 도구는 공식 NSIS 3.13 ZIP 배포본을 `output/installer-tools/nsis-3.13`에 압축 해제하고, Microsoft 공식 `vc_redist.x64.exe`를 `output/installer-tools`에 준비한다. 설치 프로그램은 네트워크 다운로드 없이 포함된 파일만 사용한다.

```powershell
./desktop/Build-Setup.ps1 -BundlePath <이번-빌드-실행폴더> -OutputDirectory <새-설치본-폴더>
./desktop/Verify-Setup.ps1 -Distribution <새-설치본-폴더>
```

기본 결과는 `output/OMNIS-Final-Setup-20261107/DVD/Setup.exe`다. DVD에 담을 파일은 `DVD` 폴더의 내용이며, `evidence`에는 원본/설치 파일 해시, 빌드·설치·실행 시험 결과를 보관한다. 빌드는 700,000,000바이트 및 4,700,000,000바이트 기준으로 전달 폴더의 실제 크기를 판정한다. `debug.log`와 화면 확인용 `sidebar.png`를 제외하고 기존 배포본의 파일을 유지한다.

검증은 한글·공백이 있는 작업 폴더에 `/TESTMODE`로 설치한다. 이 모드는 실제 설치 파일의 압축 해제와 제거 경로를 사용하면서 사용자 바탕화면·시작 메뉴·프로그램 등록을 생략한다. 실행 시험은 완전히 새 사용자 프로필, 포함된 Java/MySQL, 로컬 주소만 허용하는 브라우저 요청으로 로그인·업무 화면·개인 일정 저장·재시작 후 유지·정상 종료를 확인한다. 제거 시험은 설치된 파일만 제거하고 추가한 파일과 사용자 프로필이 남는지 확인한다. 물리적인 망 분리나 다른 PC/새 Windows의 검증과는 구분한다.

설치본에는 원본 PC의 입력 자료나 사용자 DB를 넣지 않는다. 첫 실행에 시연 DB를 만들며, 실제 자료와 로그는 `%APPDATA%\OMNIS Desktop Main\service`에 유지한다. 기존 SQLite OMNIS 1.1.12에서 자동 이관하지 않는다. demo 배포의 AI는 꺼져 있고 Ollama·모델은 포함하지 않는다. 설치 프로그램과 제거 프로그램은 이 사용자 데이터 폴더를 삭제하지 않는다.

최신 main(V41) 기반 실행본은 OMNIS Desktop Main 프로필을 사용한다. 기존 feature/fault-report 시연 DB(V35/V36의 의미가 다름)는 기존 OMNIS Desktop 폴더에 보존되며 자동 연결하지 않는다.

설치·실행 검증은 pnpm --dir desktop install --frozen-lockfile로 준비한 Playwright를 사용한다. Verify-Setup.ps1은 설치·재설치·제거와 격리된 사용자 데이터 보존을 확인한다.

## 메뉴 구성 검토 (2026-11-07)

기존 화면의 실제 목적, 데이터와 권한을 기준으로 분류했다. 사용자 관찰 실험으로 효과를 입증한 결과는 아니며, 기존 기능의 위치와 묶음만 조정했다.

```text
통합상황판       상황판 바로 열기, 업무 통계, 지시사항, 근무자 현황, 정보통신 현황
업무요청         새 요청 [업무 안내 도움말], 요청 현황 [요청한 업무 / 공유받은 업무]
업무 처리        업무등록대장 [등록 버튼], 접수 대기,
                 결재 [내 차례 / 진행 중 결재 / 처리한 결재]
일정             달력으로 바로 이동
관리             조직·인원 [조직도 / 인원], 장비·구성도 [장비 / 구성도], 문서함, 업무 유형 관리(권한별)
AI 질의응답      기존 화면
```

- **우리 부서 업무와 등록을 업무 처리로 이동:** 업무 목록에는 접수·계획·수행·종료 상태가 함께 들어 있어 달력의 하위 화면으로 두기 어렵다. 내부 등록은 다른 부서에 보내는 요청과 구분하고, 우리 부서 업무 목록의 등록 버튼으로 연결한다. 업무 처리의 기본 진입은 우리 부서 업무 목록이다.
- **관리의 다섯 탭을 세 업무군으로 분리:** 조직과 인원은 소속을, 장비와 구성도는 자산과 배치를 함께 살펴보므로 각각 두 탭으로 유지한다. 문서함은 파일 탐색 목적의 독립 화면이다. 각 업무군을 사이드바에서 바로 찾을 수 있다.
- **조회와 관리 권한은 그대로 분리:** 조직관리·인원관리·장비관리는 해당 조회 탭의 권한별 작업 링크로 진입한다. 추가 특성 편집은 기존 관리 화면의 도구를 유지한다. 업무 안내는 요청 작성 화면의 도움말, 업무 유형 관리는 관리의 권한별 메뉴, 결재 경로는 결재 화면의 작업 링크로 진입한다. 경로를 직접 열 때도 기존 클라이언트·서버 권한 검사가 적용된다.
- **유지한 통합:** 상황판과 업무 통계는 통합상황판 아래에서 각각의 화면으로 열고 중복 탭은 두지 않는다. 요청한 업무와 공유받은 업무는 같은 업무에 대한 열람 관점, 결재 세 탭은 같은 결재 문서의 처리 상태이므로 각각의 탭 구성을 유지한다. 결재 진행 목록은 본인이 올린 문서 외 관련 문서도 포함하므로 제목을 진행 중 결재로 맞춘다.
- **호환성:** 기존 URL, 쿼리 필터, 목록 복귀 주소, API와 DB를 유지한다. 일정은 단일 달력 메뉴로 단순화한다. 이전에 복원한 사이드바 여백을 유지하며 개인설정은 상단 사용자 메뉴에서 이용한다.

자동 검증은 메뉴 분류·쿼리·복귀 경로·권한 단위 검사와, 설치된 Electron에서 실제 이동·업무 처리·권한별 접근·재실행을 확인한다. 설치 검증은 격리된 합성 DB를 사용하며 실제 사용자 프로필을 변경하지 않는다.

## 최근 검증 결과와 남은 사항 (2026-11-07)

메뉴 개편 코드 `2a9896c` 기준으로 프런트엔드 검사 20개와 변경한 TypeScript 파일의 lint를 통과했다. Java WAR 빌드도 성공했고, WAR에 들어간 프런트엔드 파일 538개가 빌드 결과와 일치했다. 실제 Windows 설치본의 파일 867개를 SHA-256으로 확인했다.

격리된 합성 DB에서 메뉴·탭 이동, 목록 복귀, 권한별 관리 진입, 실제 업무 API의 요청·접수·계획·완료 결재·반려·부서 업무 등록을 확인했다. 두 번의 실행에서 일정과 업무 상태가 유지됐고 창을 닫으면 Java/MySQL이 종료됐다. 별도 제거 검사에서는 설치 파일 867개가 제거되고 사용자 프로필 파일 331개와 사용자가 추가한 파일이 보존됐다.

**동일 설치본의 무인 재설치는 대기 상태에서 끝나지 않아 검증을 완료하지 못했다.** 해당 격리 테스트 프로세스를 종료한 뒤 위 제거 검사를 별도로 수행했다. 대기 원인은 확정하지 못했으며, 재설치 성공으로 보고하지 않는다. 기존 설치를 덮어쓰는 재설치 검증은 후속 작업으로 남는다. 현재 사용 확인에는 폴더형 실행본을 권장한다.

전체 프런트엔드 lint에는 기존 오류 3개(`CalendarEventModal.tsx`, `ThemeContext.tsx`, `svg.d.ts`)와 경고 11개가 남아 있다. 검증은 현재 Windows PC에서 수행했으며, 새 Windows/다른 PC, 실제 바로가기·프로그램 등록, 물리적 망 분리, 모든 화면의 전체 CRUD에 대한 시험은 포함하지 않는다.

실행본·설치 파일·로컬 런타임·합성 DB·검증 로그는 Git에서 제외하는 `output/` 아래에 보관한다. 저장소에는 메뉴와 Electron 소스, 패키징·설치·검증 스크립트를 포함한다.

## 부서 업무 등록 진입 통합 (2026-11-08)

사이드바의 우리 부서 업무 등록 항목을 목록 상단의 같은 이름 버튼으로 옮겼다. 기존 `/approvals/new` 입력 화면과 서버의 REGISTER·결재 로직을 재사용한다. 등록 중에도 사이드바의 우리 부서 업무가 선택되고, 상단 경로와 목록으로 링크에서 검색·필터·페이지를 유지한 목록으로 돌아간다. 직접 연 등록 주소와 잘못된 복귀 주소는 기본 부서 업무 목록을 사용한다.

새 등록 제출 뒤에는 `from=mine`으로 요청자의 전체 조회 범위를 유지한 상세 화면을 열고, 별도의 `returnTo`로 부서 목록 복귀를 보존한다. 본인 결재이면 처리 건이 바로 생기지만, 다른 사람의 결재 대기 중에는 아직 처리 건이 없으므로 기존 상세의 결재 상태를 보여 준다. 요청한 업무·공유받은 업무에서 들어온 기존 상세와 다시 올리기의 동작은 유지한다.

`setup-smoke.cjs`와 `verify-registration.cjs`는 새 프로필의 Electron 실행본에서 실제 폼 등록, 검색한 목록 복귀와 새로 고침, 결재 대기·승인, 차례가 아닌 사람의 승인 거부, 일반 사용자 등록과 재시작 후 보존을 확인한다. 실제 사용자 프로필은 사용하지 않는다. 새 폴더형 실행본은 `output/OMNIS-Department-Registration-Windows-x64/OMNIS.exe`로 만든다.

## 최신 main 통합: feat/final-mvp (2026-11-08)

원격 main `8cfa20f`에서 분기하고 기존 메뉴·Electron 작업 `3a68339`를 병합했다. AI 질의응답 수정, AI 업무지원(F12 기능), 지원 화면의 입력 어댑터, V42와 갱신된 시연 데이터를 보존한다. 양쪽에서 수정한 `AppLayout.tsx`에는 AssistProvider·지원 패널과 SectionNavigation을 함께 두고, `RequestForm.tsx`에는 최신 AI 입력 지원과 목록 복귀·등록 버튼 동선을 함께 유지한다. 백엔드 소스는 해당 main과 동일하다.

최신 main의 추천 비교 시험에서 누락된 `tests/poc/ai-assist/recommend_vectors.json`은 15개 새 합성 사례로 보완했다. 기존 화면·서버 시험이 같은 파일을 사용한다. 이는 모델 품질 측정 자료가 아니다. `verify-main-features.cjs`는 최신 지원 화면 14개의 경로와 상단 AI 지원 패널, 등록 화면 이동 중 패널 유지를 확인한다. `verify-upgrade.cjs`는 이전 V41 검증 프로필의 복사본으로 V42 업그레이드와 업무·결재·일정 보존을 검사하며 원본 파일의 해시가 바뀌지 않았는지도 확인한다.

기본 프로필 `%APPDATA%\OMNIS Desktop Main`과 기존 데이터 경로는 유지한다. 최신 초기 데이터는 기존 키를 덮어쓰지 않고 업무 시연 데이터가 있으면 건너뛰므로, 기존 프로필의 조직명·시연 기록을 최신 예제로 강제로 바꾸지 않는다. 갱신된 시연 데이터를 별도로 확인하려면 새 폴더형 실행본을 다른 프로필로 연다.


한 화면 조건(콘텐츠 폭 1024px 이상·본문 폭 340 CSS px 이상·높이 440 CSS px 이상)은 유지한다. 복원된 화면은 본문 730 CSS px 미만일 때 패널 머리와 요약을 간결하게 하고 페이지당 행 수를 실제 높이로 계산한다. 작은 창에서는 핵심 지표·주의 최상위 항목과 전체 보기, 네 패널을 유지한다. 지원 범위 밖은 읽기 쉬운 세로 흐름으로 전환한다.

새 Windows 폴더형 실행본: `output/OMNIS-Classic-Operations-Windows-x64/OMNIS.exe`. 같은 폴더의 `resources`를 포함해 폴더 전체를 보관·이동한다. 기존 앱을 닫고 실행하면 Java/MySQL이 자동 시작되며 로그인 후 통합상황판과 하위 운영현황을 확인할 수 있다. 실제 사용자 프로필과 격리된 시연을 원하면 `--user-data-dir`을 지정한다. 검증 근거는 `output/omnis-restored-operations/`이며 별도 PC 설치·실제 통신체계 계측·실제 AI 모델 추론 검증과 구분한다.

운영현황 회귀 검사는 `verify-operations.cjs`의 실제 UI/API 저장·동시 수정·상황판 연동과 `verify-operations-failures.cjs`의 503/403·재시도·저장 응답 시간 초과(전송 차단 시험)·영문/다크/큰 글씨 상세 창을 포함한다. `verify-board-roles.cjs`는 기존 네 역할의 운영현황 조회 범위·등록/수정 버튼도 비교하며, `verify-upgrade.cjs`는 성공한 이전 V42 시험 프로필의 복사본만 V43으로 올리고 원본 해시를 검사한다.

## 원본 UI 일치 및 현재 프로필 38개 시연 자료 (2026-11-08)

이번 UI 변경은 위 화면 스타일 설명을 대체한다. 원본 `military_project`의 날개·별 `BrandEmblem`, 실제 Pretendard Variable 폰트, Rounded 아이콘과 공통 디자인 규칙을 적용했다. 폰트·아이콘 라이선스도 함께 제공한다. 사이드바 하단의 사용자 메뉴는 기존 언어·개인설정·로그아웃을 재사용하고, 접힌 상태/모바일에서는 상단 접근을 유지한다. 기존 여섯 메뉴·업무등록대장·안내 배치·권한·API·Java/MySQL·Electron 기동/종료 로직은 유지한다. 일반 업무를 원본의 고장·정비로 이름만 바꾸지 않는다.

새 실행본은 `output/OMNIS-Legacy-UI-Demo-Windows-x64/OMNIS.exe`이며 폴더 전체가 필요하다. 현재 `%APPDATA%\OMNIS Desktop Main` 시연 프로필에는 기존 API로 합성 체계 38개를 등록했다. 정상 30·주의 4·점검 2·장애 1·중단 1이고 정상 운용률은 79%다. 일부 체계에는 실제 생성 시각의 변경 이력도 있다. 기록 운용률은 자동 계측값이 아니다. 기존 사용자 자료와 설정을 초기화하거나 실행본에 넣지 않았다. 새로운 프로필에는 자동 등록하지 않으며, 개발 환경에서는 아래 helper를 별도로 실행할 수 있다.

`seed-operations-demo.cjs --origin <실행 중인 로컬 앱 주소> --manifest <output 안의 결과 JSON> [--dry-run]`은 Node.js에서 실행한다. 암호는 `OMNIS_DEMO_PASSWORD` 환경변수로 전달하고 실행 후 제거한다. 계정은 `OMNIS_DEMO_LOGIN`으로 지정할 수 있으며 기본값은 시연 관리자다. 자기 활성 부서의 등록 권한을 확인하고, `DEMO-OMNIS-` 코드의 기존 자료는 편집하지 않고 건너뛴다. 재실행 추가는 0건이며 코드 충돌·삭제 이력은 강제 우회하지 않는다. 로그·Git에 암호·세션을 남기지 않는다.

자세한 원본/현재 UI 대응과 데이터 경계는 `docs/UI_LEGACY_PARITY.md`에 정리했다. `capture-legacy-ui.cjs`, `verify-legacy-ui.cjs`, `verify-demo-seed.cjs`, `verify-current-demo.cjs`로 원본 격리 캡처·공통 스타일·38개 API 등록·실제 사용자 프로필을 각각 검증한다. 검증 근거와 화면은 `output/legacy-ui-demo/`이다. 큰 창은 원본 수치로 표시하고, 중간/짧은 창은 정보와 조작부를 유지하며 페이지당 행 수를 조절한다. 별도 PC 설치나 실제 AI 추론/자동 계측 검증과 구별한다.
